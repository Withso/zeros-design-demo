# Zeros Design
meta/design.toml registers this directory; meta/canvas.json owns its pages and canvas metadata. Commit this folder together. Do not gitignore it.
For authorized local Design edits, use normal Read, Write, Edit, patch or Bash tools to author HTML, CSS, assets and meta/canvas.json. No API apply, publish or mode switch is required. Cloud executions follow their composer authoring policy.
Code agents may inspect or edit this folder when the user's request calls for it. The Design tag sets the default editing target; an attached frame in Code context is normally a reference for application implementation. Provider permissions and Plan still apply.
Each page has its own folder. Create a frame by writing <page.folder>/<name>.html and adding its stable ID to meta/canvas.json frames and that page's frames array. Example frame: {"kind":"html","source":"page-1/home.html","title":"Home","x":0,"y":0,"width":390,"height":844}.
Add a page natively by appending a page record to meta/canvas.json pages and create the folder at the Design root. Example: {"id":"checkout","title":"Checkout","folder":"checkout","frames":[]}. Use a unique stable ID and title; folder must be one portable segment (1-64 letters, digits, dots, underscores or hyphens; start with a letter or digit, no trailing dot). A lowercase slug is recommended. Folder names must be unique case-insensitively, must not be meta, assets or components in any case, and must not collide with another root entry. Keep 1-64 pages and at most 1,000 frames per page; the directory has no separate frame limit. Each frame ID belongs to exactly one page and its source stays inside that page's folder. Page rename changes the title only; preserve its folder.
Keep directory, page and frame IDs and unrelated metadata. Patch existing source; canvas dimensions set its viewport. Design frames render HTML, CSS and supported local assets. Use CSS @keyframes for animation and CSS transitions for visual states. Authored scripts, inline event handlers, JSX/TSX and application logic do not run in a frame. Represent controls as visual states; live components will use separate Code layers. Normal shell, Node and Python tools may generate and validate source. Preserve stable frame IDs and viewport dimensions, and verify the actual rendered frame. When implementing an application from a frame reference, follow that application's normal source and runtime conventions. Only listed HTML files are frames. Shared tokens.css and assets stay at the Design root; link ../tokens.css from a page's HTML frame. Resolve HTML and CSS references relative to the containing source file; an existing components/<name>.html file resolves its references from the Design root.
Use Zeros Settings or Design mode lifecycle tools to create, migrate or remove registration. Preserve IDs when repairing existing source conflicts. Design API inspect, styles, validate and capture are optional helpers; visual controls edit the same source.
Save sources before canvas references. Re-read changed files before edits; do not overwrite concurrent work. Normal authorized Git operations integrate these same checkout files; saving never auto-commits.
Authoring contract. design validate warns when a frame breaks rule 1, 3, 4 or 8; warnings never block a save.
1. Classes are global or a component's, and never a second name for one. A global class lives in a Design stylesheet the frames link, or a style source; a component's class lives in its main frame's <style> and is used only inside that component and its instances. Other frames define no classes of their own. Example: .card in styles.css for every frame, .composer only in the chat-composer main.
2. Draw a state on the same markup with an attribute or a state class, never a second copy. Example: <button data-state="open"> or .btn.is-active, not a second .btn-active button. A component's hover, pressed, focus and disabled looks are its state variants: <zd-variant name="hover" zd-state="hover"></zd-variant> with :hover rules in its main.
3. Write token values as var(--name); no literal where a token holds that value. Example: color: var(--fg2), not the hex it resolves to.
4. Inline style is for one-off values and people's Style panel edits; declarations used on several elements belong in a class. Example: .row { display: flex; gap: var(--space-2); }.
5. data-oid is optional: keep existing values and add stable ones only where selection must survive a restructure. A main frame's data-oid values name the layers its controls bind, so keep them stable. Existing components/<name>.html files use data-zid and stay valid.
6. Give meaningful layers a data-name (up to 80 characters). Example: <section data-name="Pricing table">.
7. Mark markup captured or pasted from a site or an app with data-zd-captured on its root, optionally naming its source, and do not adopt its classes as this directory's vocabulary; a title such as "Settings — captured" tells people. The contract checks skip marked markup, so mark only markup that really came from elsewhere, never this directory's own. Example: <main data-zd-captured="zeros renderer">.
8. Markup repeated three or more times becomes a component: a main frame whose meta/canvas.json record adds "component":"card". Declare its options in <head><template data-zd-options>, one per line, and use them as {{ name }}. Example: <zd-option name="heading" type="text" default="Untitled"></zd-option> with <h2 data-oid="heading">{{ heading }}</h2>. A slot is a frame marked data-zd-slot="body"; what it holds is the default. Other frames place <zd-card data-oid="plans" heading="Plans"><p data-oid="plans-copy" slot="body">Body</p></zd-card>. Never add components/<name>.html; Move main to canvas turns an existing one into a main. Anything an instance should change is a control: declare it and read it in the main ({{ name }}, data-zd-if, an attribute, or var(--zd-name) in its CSS). Never write zd-style-<part> or a visual style on an instance; its own style holds only its place and size. Older ones still render, and design validate warns about them and about a control nothing reads.

## This folder
Orbit is a teaching demo. Each page shows one part of the Design tab, and the note beside each frame says what it shows, what to try and what an edit writes. Keep it that way when you change it.
- Page 10 (Lint showcase) breaks the authoring contract on purpose. Its warnings are expected; leave them unless the user asks you to fix one. Page 11 (Fixed issues) keeps edge cases that once tripped Zeros; leave them as they are.
- Reuse tokens.css, ui.css and pages.css. A page frame defines no classes of its own: put a page's classes in pages.css. A main component with options lives in its page folder with <template data-zd-options>, and meta/canvas.json registers it with "component". Slot components live in components/.
- The repository's README.md and docs/guide.md describe every frame. When you change what a frame shows, update its note and both files.
- tools/audit.sh, described in README.md, runs lint, screenshots and the audits the app does not show.
